## HIGH findings

### H5 — The H1 drop list omits `products` and `stores`: 6 of the 8 tables in the same failed-drop batch
- **Plan section:** §2 fact 6, §9.1 drop block, §9.6, §10.3 exception #1
- **Defect:** V2 fact 6 enumerates the 20260407074308 anon FOR ALL policies as orders, order_items, customers plus siblings on order_payments, order_timeline, product_variations — and §9.1 drops exactly those six. Cycle-1's verified fact (V1-critique appendix fact 4): that migration created FOR ALL TO anon policies on **eight** tables — orders, order_items, order_payments, order_timeline, **products, stores**, customers, product_variations — and 20260412170009 attempted to drop all eight. Live-DB ground truth shows the drop failed at least for orders; the plan's own assume-the-siblings-survived logic must extend to the full set. If the products/stores FOR ALL policies survived like orders' did, anon REST can **write** product rows (price tampering, deletion) and stores rows — a strictly larger hole than the one V2 closes, left open by a plan whose goal line promises the orders family closed *for good*. §9.6's zero-`TO anon` assertion never looks at products/stores, so verification will not catch it either. (Counter-evidence, noted for fairness: the intentional 2020619 SELECT-only products policy suggests the products FOR ALL drop may have succeeded — but the plan must not rest a P0 security closure on inference.) Additionally, fact 6 attributes the sibling policies to `20260408191701` (the variations DDL migration) — per cycle-1 fact 4 all eight came from `20260407074308`; the citation is garbled.
- **Evidence:** §9.1 lines 332–337 (DROP POLICY IF EXISTS list — no products, no stores); §9.6 line 404 (assertion list — same six); §2 fact 6.
- **Required resolution:** Add idempotent `DROP POLICY IF EXISTS 'Allow anonymous access to products'` / `'... to stores'` to §9.1 (20260407074308 names; harmless if already gone; the intentional 2020619 SELECT policy has a different name and survives). Extend §9.6: products has exactly one anon policy (SELECT-only, is_active-gated), stores has zero `TO anon` policies. Correct fact 6's attribution and table list.

## MEDIUM findings

### M7 — RPC 23505 handler is not constrained to the idempotency index; any other unique violation is misclassified as a dedupe
- **Plan section:** §9.1 step 1 (comment block)
- **Defect:** As written: gets 23505 after commit → exception block SELECTs the committed row by key → RETURN deduped:true. The handler is described as catching 23505 generally. A unique violation from any **other** constraint on the orders insert — most plausibly `order_number`, generated by the edge fn before the RPC call, colliding under concurrent different-key checkouts — enters the same branch: the SELECT-by-**this**-key finds no committed row, and the plan is silent on what is returned (NULL order_id in a deduped:true 200, or an opaque error). Insert-first is sound; the exception contract is not.
- **Evidence:** §9.1 lines 352–355.
- **Required resolution:** Specify: catch unique_violation, verify the constraint is `uq_orders_idempotency_key` (GET STACKED DIAGNOSTICS CONSTRAINT_NAME), re-raise otherwise; and if the by-key SELECT returns no row, re-raise — a 23505 that is not a same-key commit is an error, never a dedupe.

### M8 — Case A decrement has an uncovered shape: non-variation item on a product with zero parent rows decrements nothing and reports success
- **Plan section:** §9.1 step 3 (Case A), step 2
- **Defect:** Step 2 validates qty against `products.stock_quantity` (the all-rows aggregate — parent + variation rows together, fact 1), so validation **passes** for a product whose location rows are all variation-keyed. Step 3 Case A then decrements `WHERE product_id = p AND variation_id IS NULL` — zero rows match; the variation-ledger UPDATE applies only when the item carries variation_id; Case B applies only when the product has zero location rows. Net: order committed, nothing decremented anywhere, and because no product_locations row was written, the sync trigger never fires to recompute the aggregate — a silent oversell path. The storefront UI requires full variation selection, but the RPC contract must not depend on client behavior (the fn forwards cart items and only validates variation_id *when present*). Secondary under-specification: the FIFO decrement has no stated negative-stock guard, and step 2 validates the variation ledger while step 3 draws from location rows — the parent-row fallback is stated, but the insufficient-remainder failure semantics are not.
- **Evidence:** §9.1 lines 360–369; §6.4 (variation checks when present).
- **Required resolution:** Make decrement coverage self-checking: assert rows-affected ≥ 1 per item (or fall back to the Case-B direct products decrement when the keyed UPDATE matches nothing), guard FIFO decrements so no row goes below zero, and raise P0001 whenever the decrement cannot fully cover qty — never silently under-decrement.

### M9 — Phase 6's CREATE POLICY collides with Phase 3's identically-named policy: the migration breaks on the standard deploy path
- **Plan section:** §9.1 (drop/re-create block, lines 338–341)
- **Defect:** Phase 3 (§6.1) creates `Public can read product variations` on product_variations. Phase 6 runs `DROP POLICY IF EXISTS 'Allow anonymous access to product_variations'` (the 20260407074308 name — a different policy) and then `CREATE POLICY 'Public can read product variations'` — which already exists from Phase 3. CREATE POLICY has no IF NOT EXISTS; the Phase 6 migration errors out, blocking the entire PII-closure release. The accompanying comment (drop-then-recreate keeps this migration self-contained *if Phase 3's policy naming differs*) is self-contradictory: §6.1 of this same plan fixes the name, so it cannot differ — and if it somehow did, the CREATE would leave two public policies coexisting.
- **Evidence:** §9.1 lines 338–341 vs §6.1 line 203.
- **Required resolution:** Either add `DROP POLICY IF EXISTS 'Public can read product variations'` before the CREATE (making the block genuinely idempotent), or drop the re-create entirely — the 20260407074308-name drop is idempotent and Phase 3's policy persists; the §9.6 assertion (exactly the SELECT-only public policy) already covers the outcome.

### M10 — storefront_restore_stock is under-specified for state divergence between place and cancel
- **Plan section:** §9.1 (restore RPC comment block), §9.3
- **Defect:** The restore is specified as the reverse of step 3 with the same NULL-keyed predicates — but the reverse cannot be derived from the order alone when the world changed since placement: (a) a variation item whose decrement drew from parent rows via the fallback is reversed by crediting variation-keyed rows — per-location distribution skews (aggregate survives, but the ledger the sale actually drew from is not the one refunded); (b) Case B at place time (direct products.stock_quantity decrement) + location rows added before cancel → the sync trigger recomputes the aggregate from locations (erasing the Case B decrement), then restore adds qty → net +qty phantom stock; (c) Case A at place time + all location rows deleted before cancel → the reverse has nothing to increment and its failure semantics are unspecified. Additionally, the plan notes the woo auto_push triggers fire on decrements — restores (increments) fire them too (arguably desired), but the plan should say so.
- **Evidence:** §9.1 lines 375–380; §9.3.
- **Required resolution:** Record the decrement shape per order (e.g., a per-item ledger/case note on order_items or a restore journal row written by storefront_place_order) and have the restore replay exactly that shape; where the recorded rows no longer exist, fall back to the products-direct increment with a logged drift notice. Add one sentence acknowledging restore-path woo pushes.

### M11 — Effort total does not equal the sum of the phases
- **Plan section:** Header (line 3), §3 table, §14 M5 row
- **Defect:** Phase efforts (§3 table, confirmed in each phase's effort line): P1 4–5 wk, P2 3–5 d, P3 1–1.5 wk, P4 5–7 d, P5 3.5–5 d, P6 6–8 d. Sequential single-dev sum: 42.5–57.5 workdays = **8.5–11.5 weeks** at 5 d/wk. Stated estimate: **7.5–10 weeks** (header and M5 change-log row) — understated ~1 wk on the min and ~1.5 wk on the max. No overlap is claimed for the single-dev order (§11 reserves parallelism for the two-dev split). V1's 7–9.5 carried the same latent mismatch (cycle 1 endorsed it without summing — corrected here).
- **Evidence:** §3 lines 48–54, §11 line 460, header line 3.
- **Required resolution:** Either re-state the total as 8.5–11.5 wk, or state the intended packing/overlap explicitly. Honest-effort discipline is one of this plan's stated virtues — the header should not contradict the phase table.

### L4 — Phase 2 consumes the §7.1 route helper three phases before Phase 4 creates it

- **Defect:** §5.2 says collection cards link via the §7.1 route helper — but the pinned single-dev order is 1 → 2 → 3 → 5 → 6 → 4; routes.ts does not exist when Phase 2 executes. A literal executor hits a missing-module reference (or silently inlines a divergent constant).
- **Evidence:** §5.2 line 182 (via the §7.1 route helper); §11 line 460.
- **Required resolution:** Hoist routes.ts creation into Phase 2 (it is tiny and Phase 2 is its first consumer), or inline the constant in Phase 2 with a TODO to adopt routes.ts in Phase 4.

### L5 — The PG15 enum claim is over-broad and the migration sits one edit from an unsafe-use error
- **Plan section:** §4.1 (permission enum block, parenthetical line 108)
- **Defect:** The claim PG15 allows ADD VALUE + use in one transaction is true only in a restricted sense: PG12+ permits the ALTER in a transaction, but **comparing** the new value in the same transaction (range/equality predicates) raises `unsafe use of new value`. The plan's UPDATE survives because array_append *writes* the new value and the WHERE clause compares only the old 'stores.view' — but the plan presents the permission as blanket, and the obvious idempotency hardening (AND NOT permissions @> ARRAY['storefronts.view']) reintroduces the exact hazard.
- **Evidence:** §4.1 lines 104–108.
- **Required resolution:** Qualify the parenthetical (add-value yes; same-txn *comparison* of the new value is what PG forbids), or defensively split: ADD VALUE in this migration, the role_permissions UPDATE in a follow-up migration.

### L6 — Customer upsert still runs before the RPC: failed checkouts mint ghost customers
- **Plan section:** §9.2 (flow)
- **Defect:** The fn upserts the customer, then calls storefront_place_order; a 400 (out of stock, disabled method) leaves a created/updated customer row for an order that never existed. Pre-existing behavior, but this phase is the natural moment — the RPC is one transaction and could take the upsert inside it.
- **Evidence:** §9.2 line 388 (upsert customer → ... → single RPC call).
- **Required resolution:** Move the customer upsert into the RPC payload/transaction, or state the ghost-customer growth as accepted in §13.

### L7 — product_variations anon policy USING (true) is broader than the products-table precedent
- **Plan section:** §6.1 (policy), §10.1
- **Defect:** `FOR SELECT TO anon, authenticated USING (true)` exposes variation rows — including price — of inactive/draft products via direct REST, while the products anon read is gated `is_active = true` (2020619 precedent). The plan argues variations carry no sensitive data and activeness is enforced client-side by joining through products — a real but weaker guarantee, decided implicitly.
- **Evidence:** §6.1 line 203.
- **Required resolution:** Either scope the policy with EXISTS (SELECT 1 FROM products p WHERE p.id = product_variations.product_id AND p.is_active) to match precedent, or explicitly accept the exposure in §13 with the same reasoning given in §6.1.
