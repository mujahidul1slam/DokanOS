### BLOCKING DEFECT 2 — saving an order in DokanOS zeroes fee/tax money (found 2026-11-24)

Found by comparing the two fixtures. **This is a money-loss defect in the local UI save path, not in the sync.**

- Woo `#8869` (F02) total is **৳1** (an order fee). DokanOS stored `total = 1.00` when the worker imported it, then after the order was saved from the detail sheet the row reads `total = 0.00`, `subtotal = 0.00`, while the payment record still says `৳1` and `total_paid = 1`. **The order now claims it is worth ৳0 while a ৳1 payment is recorded against it.**
- F01 (`#8868`) is the control: it was imported with `total = 1.00` and was **never opened and saved** in the sheet. Its total is still `1.00`. So the loss happens on the local save, not on import.
- Two independent contributing facts, both real:
  1. **Fee lines are never mapped.** A search across `supabase/functions/woocommerce-worker/index.ts`, `src/lib/woocommerceConnector.ts` and `src/lib/woocommerceWorkerValidation.ts` finds **no** reference to `fee_lines`, `fee_total`, `tax_lines` or `cart_tax`. Only `line_items` is read (`supabase/functions/woocommerce-worker/index.ts:156`). So a fee-only order imports with zero item rows.
  2. **The sheet recomputes totals from line items alone.** `src/components/orders/OrderDetailSheet.tsx:869-870` is `computedSubtotal = activeItems.reduce((s, i) => s + i.quantity * i.unit_price, 0)` and `computedTotal = computedSubtotal - discount + shippingCost`; the save path writes `subtotal: computedSubtotal` and `total: computedTotal` at `:1081-1082`. With zero item rows and zero shipping, `computedTotal` is **0**, so the save overwrites the imported ৳1 with ৳0.
- Scope of harm: any order carrying value that is **not** an `order_items` row — fees, tax, coupons applied as fees — loses that value the moment a staff member opens the order and presses **Save Changes**. The order's own total and the payment record then disagree.
- Not proven: whether tax (as opposed to fees) is also dropped on save for a normal item-bearing order. That needs a fixture with real line items plus tax; it was not created.
- **Remediation — LOCAL FIX DONE 2026-11-24, NOT DEPLOYED.** The save path no longer derives money from the line items unless the line items were actually edited. New pure helper `src/lib/orderTotals.ts` (`computeOrderTotals`) carries the stored `subtotal` when `itemsTouched` is false and only recomputes from the item list after a real add/remove/re-price/re-quantify. `src/components/orders/OrderDetailSheet.tsx:868-891` now computes `itemsTouched` (compares `editedItems` against the loaded `items`, honours `deletedItemIds` and `_isNew`) and feeds `computeOrderTotals` with `taxAmount: order.tax_amount`; the write at `:1081-1082` therefore persists the preserved money. Tax is now part of the total too, which it previously was not. Tests: `src/test/orderTotals.test.ts` (5 cases, pure contract) and `src/test/orderDetailFeeTotal.test.tsx` (component: a fee-only order saves `total: 1` and `subtotal: 1`). `npm run typecheck` clean; `npx vitest run src/test/orderTotals.test.ts src/test/orderDetailFeeTotal.test.tsx src/test/orderDetailWooStatusSafety.test.tsx src/test/orderDetailSheetScope.test.tsx` → 14 passed. **Not deployed** — the Vercel frontend still runs the old bundle, so the live defect is still live until a frontend release.
- Blast-radius check on real data before changing the formula: `SELECT count(*) FILTER (WHERE round(total,2) <> round(subtotal - discount + shipping_cost + tax_amount,2)) FROM public.orders WHERE deleted_at IS NULL` → **0 of 4272** orders would change value. So the new formula agrees with the stored data everywhere except the fee-only case it fixes.
- Still open: whether tax on a **normal item-bearing** order behaves the same way is unproven; the helper now includes `tax_amount` in the total, but no fixture exercised it. Also unproven whether the worker should map Woo `fee_lines` into `order_items` (cause 1 above) — that is an import-fidelity gap, separate from this save-path fix.
- Evidence of the original loss: `SELECT order_number, total, subtotal FROM public.orders WHERE order_number IN ('EE-8868-W','EE-8869-W')` → `EE-8868-W` `1.00`/`1.00`, `EE-8869-W` `0.00`/`0.00`; timeline `Payment of ৳1 via bkash confirmed. Order fully paid.` at `2026-11-24T15:51:26Z`; payloads `47e98e16…`, `d3841e0d…`, `61c1de98…`, `c3c821a4…` all carry `total = "1"`, `n_items = 0`, `n_fees = 1`, `subtotal = null`.
